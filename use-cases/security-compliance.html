Scenario 1 Compliance · Drift

The control that passed the audit and failed the next week

Series B fintech · SOC 2 Type II · 2 security engineers · AWS + EKS

The situation

The SOC 2 Type I audit went well: branch protection was on, CloudTrail logged every region and no containers ran privileged. Two weeks later a developer disabled required reviews on the main repository to merge an urgent fix and forgot to turn it back on. A month later a debugging sidecar with privileged: true was added and never removed. Both surfaced in the Type II observation window — as exceptions.

Why it hurts

  • Type II audits test that controls operated throughout the period, not on one day.
  • Regressions were invisible until the auditor sampled them.
  • Each exception required written management responses and remediation evidence.

How Netpin handles it

  1. Continuous controlsControls re-run automatically every 6 hours and after discovery — branch protection, required reviews, privileged containers, CloudTrail and many more.
  2. Regression detectionPosture regression drift flags a security violation that was not present in the previous scan.
  3. Alert the moment it happensFailing critical controls raise alerts to the security channel, with the resource and evidence.
  4. One result, every frameworkThe privileged-container result counts for CIS Kubernetes, Pod Security Standards, NSA/CISA, PCI DSS and NIST at once.
  5. Proof of remediationThe timeline shows when the control failed and when it passed again.

What changes — and what to measure

Time a control stays failedHours, not months
Audit exceptionsCaught and closed before the auditor samples them
Evaluated coverageShare of requirements with real evidence

Scenario 2 Prioritisation · Explain & Fix

Four hundred findings, two engineers, one week

Healthtech scale-up · new CISO · first security assessment of 5 clusters and 3 AWS accounts

The situation

The first scan with an open-source scanner produced over four hundred findings. The two-person security team triaged for a week, opened sixty tickets and got eight fixed — developers pushed back that most were "not real", including findings on system namespaces they did not own.

Why it hurts

  • Flat severity lists hide the few issues that matter.
  • False positives on system components destroyed credibility with developers.
  • Tickets lacked context, so fixes were slow or wrong.

How Netpin handles it

  1. Severity-weighted scoringA failed critical control weighs 10, high 5, medium 3, low 1 — one critical gap moves the score more than many low ones.
  2. Built-in exemptionsSystem namespaces such as kube-system, built-in RBAC roles and cert-manager challenge ingresses are exempt automatically.
  3. Data missing ≠ failedControls Netpin could not evaluate are shown as data missing, with the permission needed.
  4. Fix these firstControls ranked by weighted failures across every resource.
  5. Explain & Fix packetsEach finding comes with what is wrong, why it matters, affected resources, steps and verification — tickets developers can act on.

What changes — and what to measure

Critical failuresThe only number that matters in week one
Developer-accepted fixesHigher with context and no system noise
Weighted score trendPer framework, week over week

Scenario 3 Supply chain · Source control

Proving the software supply chain is under control

Developer-tools company · 140 repositories · customers asking about supply-chain security

The situation

After several widely reported supply-chain attacks, enterprise customers started asking how code reaches production: Are reviews required? Can admins bypass them? Is secret scanning enabled? Are dependencies updated? With 140 repositories created over five years, settings were inconsistent and nobody had a full picture.

Why it hurts

  • Answers varied by repository and nobody could produce a complete list.
  • Admins routinely bypassed branch protection.
  • A forgotten public repository contained internal configuration.

How Netpin handles it

  1. Connect GitHub or GitLabRepository settings are read with a token that can see administration settings.
  2. Supply-chain controlsBranch protection, required reviews, stale-review dismissal, code owners, status checks, admin enforcement, force-push and deletion, signed commits, secret scanning, dependency updates and visibility.
  3. Mapped to frameworksResults count towards the CIS Software Supply Chain guide, SOC 2 CC8.1 and ISO 27001 change management.
  4. CI and GitOps checksWorkflow health, Jenkins over HTTPS and Argo CD sync state.
  5. Deploy GateOnly code that passed your pipeline policy reaches production; overrides are audited.

What changes — and what to measure

Repositories with full protectionTarget 100% of production repos
Admin bypassesVisible per repository
Supply-chain framework scoreTracked over time

Questions teams like yours ask

Which frameworks are supported?

CIS AWS Foundations 3.0, CIS Kubernetes 1.9, Pod Security Standards, NSA/CISA Kubernetes Hardening 1.2, SOC 2, PCI DSS 4.0, HIPAA Security Rule, ISO/IEC 27001:2022, NIST SP 800-53 Rev. 5 and the CIS Software Supply Chain guide.

Does Netpin replace our auditor or GRC tool?

No. Netpin automates the technical controls and keeps evidence current. Requirements that need documents (policies, training, DR tests) are listed as manual evidence for your GRC process.

How often are controls evaluated?

Automatically every 6 hours for projects with fresh inventory, after discovery, and on demand.

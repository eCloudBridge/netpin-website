Scenario 1 Drift · Deploy Gate

The 2am hotfix that broke checkout three days later

Seed-stage marketplace · 6 engineers · one EKS cluster · Helm + GitHub Actions

The situation

Checkout started failing at 2am. The on-call engineer ran kubectl set image to roll out a hotfix build and raised the memory limit with kubectl edit. It worked, everyone went back to bed, and nobody updated the Helm chart. Three days later a routine release deployed the old image and the old memory limit — and checkout failed again, at lunchtime, in front of customers.

Why it hurts

  • The second outage was entirely self-inflicted and avoidable.
  • Nobody could say exactly what had been changed by hand, so the post-mortem took a day.
  • Confidence in releases dropped; the team started avoiding Friday deploys altogether.

How Netpin handles it

  1. Detected within 15 minutesNetpin's runtime drift sweep compares the live Deployment with the Helm release manifest and flags two runtime overrides: the image and the memory limit.
  2. AttributedKubernetes field managers show the changes came from kubectl-set and kubectl-edit, so they are counted as manual changes with the time they happened.
  3. ExplainedThe finding shows desired vs live values, the services behind the Deployment and that it is internet-facing.
  4. Fixed properlyNetpin offers two paths: revert (helm rollback) or adopt — a values snippet with the live image tag and limit to commit to the chart.
  5. Protected next timeIf a release is about to overwrite open drift, Deploy Gate flags a drift overwrite and never shows it as a plain approval.

Scenario 2 Compliance · Executive

Answering the first enterprise security questionnaire

Series A B2B SaaS · 15 engineers · AWS + EKS · first enterprise deal in legal review

The situation

The deal was nearly signed when the customer's security team sent a 180-question questionnaire and asked for a SOC 2 roadmap. Questions like "Is MFA enforced for all privileged users?", "Are production changes reviewed?" and "Is data encrypted at rest?" had no confident answers. The CTO spent two weeks clicking through the AWS console and still was not sure.

Why it hurts

  • Sales cycle stalled; the deal slipped a quarter.
  • Answers were based on memory, not evidence — a risk if the customer ever audits them.
  • Real gaps (an S3 bucket without a public-access block, no CloudTrail in one region) were found by accident.

How Netpin handles it

  1. Connect read-onlyAdd the AWS account with the SecurityAudit managed policy, the EKS cluster and GitHub.
  2. One scan, ten frameworksNetpin evaluates every control and maps results to SOC 2, ISO 27001, CIS AWS, CIS Kubernetes and more. Missing data is shown as missing, never as a pass.
  3. Fix these firstControls are ranked by weighted failures: root MFA, CloudTrail multi-region, S3 public access, privileged containers, branch protection.
  4. Evidence on demandEach result includes the resource, the evidence and every requirement it satisfies — answers backed by data, not memory.
  5. Tell the storyThe Executive Brief summarises audit readiness per framework in plain language for the customer and the board.

What changes — and what to measure

Weeks → hoursTime to produce an evidence-backed security posture
Weighted scoreSOC 2 readiness you can track weekly
Critical failuresShould reach zero before the auditor arrives

Scenario 3 Cost · Kubernetes

Runway is shrinking and the cloud bill keeps growing

Seed-stage AI startup · 8 engineers · GKE + AWS · $14k/month cloud spend and rising

The situation

The cloud bill grew 70% in two quarters while traffic grew 20%. Node pools had been scaled up during a load test and never scaled down, three staging clusters ran all weekend, workloads requested four times the CPU they used, and a handful of unattached disks from old experiments were still billing every month.

Why it hurts

  • Every extra $5k a month is roughly a month of runway per year.
  • Nobody could say which team, service or environment owned the growth.
  • Earlier attempts to "just rightsize" broke a service and were rolled back.

How Netpin handles it

  1. Priced resource by resourceEvery instance, volume, IP, load balancer, database and node is priced; when billing access is granted, numbers are calibrated to the actual bill.
  2. Kubernetes allocationNode cost is split across workloads by request or p95 usage, so idle capacity and over-requested workloads are obvious.
  3. Savings that add upRemove waste first (unattached disks, idle IPs), then modernise (gp2 → gp3), schedule non-production to office hours, and only then commit — each applied to the remaining cost so nothing is double counted.
  4. Safe rightsizingRecommendations use p95 usage plus headroom; capacity freed only counts as savings when a node can actually be removed.
  5. ForecastA month-end forecast with a 95% range and anomaly detection, so the next surprise is caught in days, not at month end.

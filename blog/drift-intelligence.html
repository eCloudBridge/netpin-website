It is 2:07am. Checkout is failing. The on-call engineer runs kubectl set image to roll out a hotfix build, the errors stop, and everyone goes back to bed. Nobody updates the Helm chart. Three days later a routine release ships the old image again — and checkout breaks for the second time this week.

That gap between what your code says and what is actually running has a name: drift. Every team has it. Most teams cannot see it. Netpin's Drift Intelligence finds every instance of it across Kubernetes, Helm, Argo CD and Terraform, and tells you who caused it, what it affects and exactly how to fix it.

What drift is — and why it is dangerous

Drift is any difference between the state you declared and the state that is running. The declaration might be a Kubernetes manifest, a Helm chart, an Argo CD application or Terraform code. The running state is whatever the cluster or cloud reports right now.

Drift happens for ordinary reasons: an emergency hotfix, a quick security-group change in the AWS console, a Terraform pull request that was merged but never applied, a GitOps controller that cannot reconcile, or an operator that quietly rewrites a field. Each one is reasonable in the moment. Together they create three serious problems:

  • Hidden risk. A hand-made change can open a port to the internet, run a container as root or remove a memory limit — without code review, without a security scan, without anyone noticing.
  • Surprise outages. The next deployment silently overwrites the live fix (like the checkout story above), or fails because reality no longer matches what the pipeline expects.
  • Audit gaps. Changes made outside the approved process break change-management controls such as SOC 2 CC8.1, ISO 27001 A.8.32 and PCI DSS 6.5.1.
"Your Git repository describes the infrastructure you meant to build. Drift is the infrastructure you actually have."

How Netpin detects drift

Detection is a read-only pipeline that runs automatically — runtime drift every 15 minutes, Terraform drift every hour — and immediately when you click Run drift detection. Optionally, a live refresh re-reads every connected cluster and cloud account first, so changes made seconds ago are caught.

  1. Collect and redact. Live configuration is read through the Kubernetes and cloud APIs with the credentials you connected. Secret values, tokens and private keys are stripped before anything is stored.
  2. Resolve the desired state. For each resource Netpin finds the most authoritative declaration (next section).
  3. Compare declared fields only. Fields that Kubernetes or the cloud fill in on their own — status, resource versions, timestamps, defaults, and replica counts managed by an autoscaler — are ignored. Lists are matched by key, so re-ordering containers is not drift.
  4. Classify and score. Each difference gets a drift type, a category (security, network, capacity…) and a severity based on what changed.
  5. Explain and attribute. A plain-language explanation, the probable cause with a confidence level, and who made the change.
  6. Measure impact. Netpin walks the dependency graph to find the services, shared configuration and public endpoints that are affected.

Baselines move forward automatically when a change arrives through an approved path — a new Helm revision or a fresh kubectl apply. A hand edit does not move the baseline; it becomes drift.

Terraform: the three-way comparison

terraform plan compares state with the cloud. That tells you something is different — but not whether someone clicked in the console or whether a merged pull request was never applied. Those need opposite fixes.

Netpin adds the third leg: your code. It finds repositories with .tf files, evaluates variables, .tfvars, locals and modules so values are concrete, skips attributes in lifecycle.ignore_changes, loads the state from your backend, and compares all three per attribute.

Example — a security group opened in the console
Code and state allow port 443 from 10.0.0.0/8. The cloud has an extra rule: port 22 from 0.0.0.0/0. Code = state ≠ cloud, so it is an out-of-band change, severity critical (public SSH). CloudTrail shows AuthorizeSecurityGroupIngress by an IAM user from the AWS console. Netpin offers terraform apply -target=aws_security_group.api to revert, or the HCL block to keep the rule.

Who changed it?

Every finding answers the first question in any incident review. Netpin uses the platform's own audit trail — no agent required:

  • Kubernetes records which tool last wrote each field (managedFields): kubectl-edit, kubectl-patch, helm, argocd-controller, an autoscaler or an operator — and when.
  • AWS CloudTrail shows the IAM user or role and whether the change came from the console, the CLI, an SDK or Terraform.

Changes made by people are counted as manual changes — a number worth watching. Changes from automation are labelled with the tool.

What does it affect?

A one-line change to a ConfigMap sounds harmless — until you learn that two services mount it and one of them is public. Netpin builds a dependency graph from live specifications (Service selectors, Ingress routes, mounted ConfigMaps and Secrets, ServiceAccounts, autoscalers, NetworkPolicies, Helm ownership) and walks it from the drifted resource.

  • Affected if this changes — everything that depends on the resource.
  • Shares configuration or identity with — workloads using the same ConfigMap, Secret or ServiceAccount, where a change for one silently changes the others.
  • Internet-facing paths — routes from a public host down to the resource.
  • Impact score — a 0–100 summary that weighs closer and more critical resources higher and adds points for shared configuration and public exposure.

How serious is it?

Severity depends on what changed. Privileged containers, host networking, RBAC rules, public exposure, encryption and IAM are rated high or critical; a label or capacity tweak is usually medium or low. Each open finding then lowers a drift score by a deterministic amount, shown on the finding with its full rationale:

The formula
deduction = base(severity) × criticality × duration × recurrence × blast radius × history × confidence
criticalitycritical 2.5 · high 1.8 · medium 1.0 · low 0.5
duration< 1 day 1.0 · 1–7 days 1.2 · 7–30 days 1.5 · > 30 days 2.0
recurrence+15% each time it comes back, up to +75%
blast radius0.5 (isolated) to 1.0 (wide reach)
history×1.2 if this resource caused an incident before
Example — one finding
A high severity drift on a high-criticality Deployment, open 3 days, seen twice, blast radius 60, confidence 0.9: 10 × 1.8 × 1.2 × 1.15 × 0.8 × 0.9 = 17.88 points. Leave it a month and it costs 29.81 — old drift is expensive drift.

The drift score (0–100, higher is better) combines ten weighted dimensions — configuration and security drift weigh the most. 80+ is healthy, 60–79 is a warning, below 60 is critical.

Netpin never applies a fix on its own. When a complete scan sees live matching desired again, the finding resolves automatically; if a source could not be read, it waits rather than guessing.

Drift, your IDI and Deploy Gate

Drift is not a separate silo. It feeds the rest of Netpin:

  • Infrastructure Debt Index. Open drift lowers infrastructure health and security posture. The Impact on IDI tab shows exactly how many points drift costs and what your score would be without it — the easiest way to justify fixing drift first.
  • Deploy Gate and pre-flight risk. Before a release, Netpin checks the target for open drift. A deployment that would overwrite a live hotfix is flagged as a drift overwrite and never shown as a plain "allow". In production, a drift score below your threshold (60 by default) blocks the release.
  • Alerts. Critical and security drift raise deduplicated alerts to Slack, PagerDuty or email, with escalation if nobody acknowledges them.
  • Compliance. Drift on a security-sensitive field usually also fails a compliance control — you see both, linked.

Security and privacy

  • Read-only. Netpin uses get and list permissions only and never writes to your clusters or clouds.
  • Secret values are never stored. Kubernetes Secrets are reduced to names and keys; sensitive values in any configuration, Helm release or Terraform state are redacted before storage.
  • Short-lived credentials. Managed clusters on EKS, GKE, AKS and DigitalOcean are reached with tokens minted on demand and kept only in memory.
  • No agent required. Everything works through the Kubernetes and cloud APIs.

Getting started

  1. Connect your sources. A cloud account (clusters are discovered and connected automatically), any other Kubernetes cluster, your Git provider and Argo CD.
  2. Grant read access. Cluster read RBAC; for full cloud coverage add cloudtrail:LookupEvents (attribution) and read access to your Terraform state bucket.
  3. Run drift detection. Resources declared by Helm, kubectl or Terraform are compared immediately; everything else gets a baseline on the first scan and reports drift from the next change.
  4. Work the queue. Start with critical and security drift, use the generated fixes, and watch the drift score and IDI recover.

FAQ

Will Netpin flood me with noise?

No. Only fields you declared are compared; server-generated fields, defaults and autoscaler-managed replicas are ignored. Intentional changes can be accepted as the new baseline, and suppression rules hide fields you always change at runtime.

Why did my first scan show almost no drift?

Resources without a manifest, Helm release or Terraform declaration get a baseline on the first scan. Drift on those is reported from the next change onward. Declared resources are compared immediately.

How fast is drift detected?

Within 15 minutes for Kubernetes and an hour for Terraform — or instantly with Run drift detection and live refresh.

What is the difference between drift and a compliance failure?

Drift means a resource no longer matches its own source of truth. A compliance failure means it breaks a security rule, whatever the source says. A hand-added privileged: true is both.

Which Terraform backends are supported?

S3 state is read with the connected AWS account, and committed state files are supported. For backends Netpin cannot read yet, the code-to-cloud comparison still runs.
